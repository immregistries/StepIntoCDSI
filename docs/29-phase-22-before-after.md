# Phase 22 Before/After: The SupportingDataModel/DataModel Split

This is the durable, committed record Phase 22 (`StepIntoCDSi-Specification-Reference-Module-Plan.md`) requires before that phase is considered done - not a summary rewritten later, but the actual measurements, in the order they were taken, including the one that turned out to be a measurement mistake rather than a real result. Phase 23 (Build the Phase B Progress Story) will read this back as its first seed entry once that tooling exists; this file is written to survive that reading on its own, without the surrounding chat session.

## What changed

`DataModelLoader.createDataModel(String supportingDataSet)` re-parsed the entire Supporting Data ZIP from scratch on every call, with no caching anywhere. `DataModel` mixed that static, load-once Supporting Data (CVX map, antigen map, vaccine-group map, antigen series list, schedule list, live-virus conflict list, observation map) with per-forecast-run mutable state in one class.

The change: a new `SupportingDataModel` class holds exactly the nine fields `DataModelLoader` populates from the ZIP. `DataModel` now holds only per-run mutable state plus a reference to a `SupportingDataModel`. `DataModelLoader` caches one `SupportingDataModel` per distinct `supportingDataSet` string for the JVM's lifetime (a plain `ConcurrentHashMap`, `get`-then-`putIfAbsent`) and hands back a fresh `DataModel` on every call. Every existing public method on `DataModel` for the nine migrated fields (`getCvxMap`, `getOrCreateAntigen`, `getVaccineGroupList`/`setVaccineGroupList`, etc.) is kept as a thin delegate onto the shared `SupportingDataModel`, so none of the ~34 Phase 21 spec-conformance test files that build fixtures by mutating these collections directly needed to change. Three fields that look like Supporting Data by name but are confirmed (by exhaustive grep) never populated by the loader - `DataModel.immunityList`, `DataModel.contraindicationList`, `clinicalGuidelineObservationMap` - were deliberately left exactly where they were; moving them was unnecessary and would have touched already-documented, out-of-scope gaps.

No clinical logic, decision-table behavior, date calculation, or Supporting Data interpretation changed. Nine private `DataModelLoader` methods that build XML into a `DataModel` were mechanically retyped to build into a `SupportingDataModel` instead (their bodies were untouched - only the parameter type and the identifier it's referred by changed); two more (`readImmunity`, `readContraindications`) had an already-unused `DataModel` parameter dropped outright.

### A pre-existing, unrelated issue found and fixed while establishing this baseline

Before any FITS run could even start, `ReferenceSetVerifier` rejected the active reference set (`acip-4.6-sd-4.65-fits-8183b45d`, created 2026-09-01): its recorded FITS fixture checksum no longer matched the committed fixture content. Case count was unchanged (4,896 = 4,896 - nothing added or removed), and the root cause traced to fixture files checking out with CRLF line endings under `core.autocrlf=true` (confirmed by comparing `git show HEAD:<file>`, LF, against the working-tree copy, CRLF, byte-for-byte) - `cdsi-fits-tests/src/test/resources/fits/` had no `.gitattributes` protection against this, unlike `cdsi-reference/supporting-data/versions/**/source/**`, which was already guarded for the identical reason. Fixed by adding the same `binary` rule for the fixture tree, forcing a fresh checkout, and regenerating the reference set (new id `acip-4.6-sd-4.65-fits-222cc1c7`; the old one marked `status: retired` with a note, not deleted). The gap between the *original* `8183b45d` hash and the post-line-ending-fix hash was never fully root-caused and predates this investigation - not a concern for Phase 22, since fixture content and case count were otherwise confirmed unaffected. This fix was committed separately (`371decb`), before Phase 22's own code changes.

## A measurement mistake, corrected before trusting the result

The first "after" FITS run (`mvn -pl cdsi-fits-tests test -Dtest=FitsFixtureTest`, run immediately after finishing the `DataModel`/`DataModelLoader`/`SupportingDataModel` split) showed **identical case-level results** to the baseline - genuinely reassuring - but **essentially unchanged runtime** (502.5 s test-method time, 8m27s total build time). That did not match the isolated timing evidence (below), which shows the fix working exactly as designed. The cause: `cdsi-fits-tests` depends on `cdsi-engine` as an installed Maven artifact (`~/.m2/repository/.../cdsi-engine-5.3.4.jar`), not on the sibling module's `target/classes` directly, and `mvn install` had not yet been run against the changed `cdsi-engine` source - so that first "after" FITS run silently exercised the **old, pre-Phase-22 jar** the entire time. (This was also caught structurally: two new Phase 22 regression tests, written to reference `DataModel.getSupportingDataModel()`, failed to *compile* against the stale jar with "cannot find symbol: class SupportingDataModel" - a hard signal, not a guess, that the jar was stale.) Running `mvn -pl cdsi-engine install -DskipTests` and re-running the FITS suite produced the real result below. Recorded here rather than quietly discarded, because a future reader comparing this file to a raw run log should be able to see why one FITS run in the history doesn't match the others.

## Isolated timing evidence (the caching mechanism itself, independent of any Maven module-resolution confusion)

A standalone probe run directly against `cdsi-engine/target/classes` (bypassing Maven's module dependency resolution entirely) measured `DataModelLoader.createDataModel(String)`'s per-call cost before and after caching, in the same warmed-up JVM:

- Steady-state **uncached** parse (bypassing the cache via reflection into the now-private `loadSupportingDataModel`, i.e. what every one of the 4,896 original calls did): converges toward roughly 85-146 ms/call after JIT warmup, still trending down at 500 iterations - genuinely expensive, real work (DOM parsing, ~30 domain-object trees built from scratch).
- Steady-state **cached** call (the real `createDataModel` path, post-Phase-22): **0.002 ms/call** - a ~40,000-70,000x reduction, and by construction zero additional parses no matter how many more calls follow.

This confirms the fix does exactly what it was designed to do. It does **not**, on its own, predict the full-suite runtime improvement below - see the next section for why the two numbers don't need to match, and don't.

- FITS, reference set `acip-4.6-sd-4.65-fits-222cc1c7`, commit `9ccbf22`: **4,896 total cases - 3,364 passed, 1,531 failed-assertion, 1 execution-error, 0 skipped** internally - identical to baseline in every count. Run bundle `2026-09-07T165702-910277600Z-9ccbf22-acip-4.6-sd-4.65-fits-222cc1c7`, started `16:57:02.910Z`, finished `16:57:42.787Z` - **elapsed 39.9 s**.
- `cdsi-web`: builds and its test suite passes cleanly against the new `DataModel`/`SupportingDataModel` surface (it only ever reaches Supporting Data through `DataModelLoader.createDataModel`, so this was expected to be a formality, and was).
- Three new regression tests, all green: `DataModelLoaderCacheTest` (`cdsi-engine`) proves repeated calls with the same `supportingDataSet` string share one `SupportingDataModel` while still returning distinct `DataModel` instances, and that two different bundled sets (4.64 and 4.65 are both bundled) get different `SupportingDataModel`s; `CaseOrderIndependenceTest` (`cdsi-fits-tests`) runs two genuinely different real fixtures (a newborn DTAP case and a 15-month-old MMR case) back to back in both orders through the now-shared cache and asserts identical results per case regardless of order; `SupportingDataModelUnmutatedAfterRunTest` (`cdsi-fits-tests`) fingerprints a shared `SupportingDataModel` before and after running a real batch of cases through it and asserts the fingerprint - sizes plus sorted keys/names of all nine migrated fields, plus total series-dose count - is unchanged.

## The headline number

**Full FITS suite runtime: 457.5 s -> 39.9 s, an 11.5x reduction, with byte-identical results on every count measured.** (The build's own reported numbers - 465.3s -> 48.3s test-method time; 7m53s -> 53.96s total Maven wall time including startup/shutdown - tell the same story; the `run.json` bundle timestamps above are used as the headline because they're the more precise, tool-recorded measurement Phase 17/18's diagnostic bundle already exists to provide, rather than a stopwatch on Maven's own console output.)

Same clinical results. Same spec-conformance test results. A materially faster feedback loop for every Phase 21 Role B round still to come, each of which requires a full FITS run before and after its own fix.

## What this round does and doesn't tell you

It tells you the specific architectural boundary this phase set out to build - shared, cached, read-only-in-practice `SupportingDataModel`; fresh `DataModel` per run - is real, correct on every case in the fixture set, safe under back-to-back cases in either order, and does not leave the shared object mutated afterward. It tells you the fix earns its keep on wall-clock time by a wide margin.

It does not tell you anything about clinical correctness one way or the other - that was never the goal, and the identical failure/pass counts on both sides are the proof the goal was met, not a finding to investigate. It also does not fully explain the isolated per-call timing numbers against the full-suite runtime improvement in a single tidy equation (JIT behavior in a long-lived surefire JVM warms considerably beyond what a short isolated probe shows), and it does not identify what now dominates the remaining ~40 seconds of full-suite runtime - plausibly genuine per-case forecast computation and JUnit5's own per-case dispatch overhead, neither investigated further here, since neither was this phase's job. That is left as an open question for whoever next looks at FITS suite performance, not a Phase 22 deliverable.
