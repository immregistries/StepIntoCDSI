# Decision Tables

> **Review status:** draft.

## What this covers

The notation every "Table N-M: <business question>?" grid in Chapters 4-9 uses, and how `cdsi-engine` implements that notation generically once rather than once per table. Source: Logic Specification for ACIP Recommendations v4.6, sections 2.10 "Processing Model" and 2.11 "Decision Table Overview" (pages 20-22) - there is no formal extraction for Chapter 2 (out of the Phase 3-5 pipeline's scope, which covers Chapter 3 and Chapters 4-9), so this section was read directly from the source PDF rather than from a generated `extracted/sections/*.txt` file.

## Explanation

**[SPEC]** Section 2.10 explains *why* the specification's rule logic is written the way it is: "the logic definitions focus on the functionality necessary to evaluate and forecast based on one specific target dose and one specific vaccine dose administered... the processing model describes, in a technology-neutral fashion, the algorithms necessary to merge multiple executions and results of the logic definitions." In other words: decision tables (and the business rules around them) are deliberately written as if only one dose and one target dose exist at a time - see [target-dose.md](target-dose.md) - and it's the *processing model* (Chapter 4, and the orchestration logic in every `LogicStep.process()`) that's responsible for looping this single-item logic over a patient's full history. Conflating "what does this decision table decide" with "how many times, and in what order, does it get invoked" is exactly the kind of confusion this separation is meant to prevent.

**[SPEC]** Section 2.11 describes the notation itself using two illustrative, non-clinical examples (a "should I wash my car?" table and a "what exercise today?" table) rather than a real CDSi table, precisely so a reader learns the format before encountering clinical content:

- **Conditions + Answers = Rules; Rules determine Outcomes.** A table lists one or more yes/no-style *conditions* as rows; each *rule* is one column, giving a specific combination of condition answers; the *outcome* row(s) say what happens when a given rule's combination is matched.
- A dash (`-`) in a condition/rule cell means that condition doesn't matter for that rule ("don't care") - e.g. in the car-wash example, "Is the car wash open? No / - / -" means the second and third rules don't care about that condition at all.
- A table may have a **default outcome**, which fires only when none of the explicit rules match (the car-wash example's default is "Yes, wash the car" - the fallback when nothing is preventing it).
- The majority of Chapters 4-9's tables use this row-of-conditions/column-of-rules style. A second style exists (a plain row-heading × column-heading grid, illustrated by the "what exercise today?" example) but wasn't observed in any of the actual CDSi decision tables documented across Chapters 3-9 in this pass - if one turns up later, it would need different structural treatment than the condition/rule grids `extract_tables.py` currently targets.

**[IMPLEMENTATION]** `cdsi-engine`'s `org.openimmunizationsoftware.cdsi.core.logic.items.LogicTable`/`LogicCondition`/`LogicOutcome`/`LogicResult` classes are the one generic mechanism every decision table in every `LogicStep` is built from - individual steps (like [6.4 Evaluate Age](../steps/06-04-evaluate-age/index.md)'s inner `LT` class) only supply the specific conditions, the specific rule grid, and the specific outcomes; the matching algorithm itself lives in `LogicTable.evaluate()`, once. `LogicResult` has eight values - `YES`, `NO`, `ANY` (the code's name for the spec's "-"/don't-care), `UNKNOWN`, `EXTRANEOUS`, `ZERO`, `ONE`, `MORE_THAN_ONE` - a broader vocabulary than section 2.11's own simple examples show, because it has to cover every condition-answer type that appears anywhere in Chapters 5-9 (e.g. `UNKNOWN` for indeterminate indications in [5.1](../steps/05-01-select-relevant-patient-series/index.md)/[7.3](../steps/07-03-determine-contraindications/index.md), `ZERO`/`ONE`/`MORE_THAN_ONE` for the counting-style conditions in [8.2](../steps/08-02-identify-one-prioritized-patient-series/index.md)'s Table 8-3). `LogicTable.getLogicOutcomeDefault()`/`setLogicOutcomeDefault()` is the code equivalent of the spec's "Default:" outcome row.

## Where it applies

Every decision table in every step package under [`steps/`](../steps/) is an instance of this pattern - this document exists so none of those packages need to re-explain the notation itself, only their own specific conditions/rules/outcomes.

## Open questions

- **A real, verified engine-level finding, not specific to any one step - found, not fixed, per current project direction (tracked for a later dedicated pass):** `LogicTable.evaluate()` contains a safety check that would flag more than one rule column matching simultaneously when there's no default outcome to fall back on - exactly the situation section 2.11's notation assumes can't happen, and which the project's own `docs/12-decision-table-semantics-and-rule-evaluation-order.md` calls "almost always an implementation defect, not a valid CDSi state." That check's `throw new IllegalStateException(...)` is **commented out** (`LogicTable.java`, inside `evaluate()`, immediately after the `validColumnCount != 1 && logicOutcomeDefault == null` condition). As written, if two rule columns both match, `evaluate()` calls `perform()` on *both* outcomes in table order, with the later one's state changes silently taking precedence and no warning logged anywhere. This is a property of the shared mechanism every decision table in the system depends on, not a one-off gap in a single step - worth prioritizing appropriately whenever gap-fixing work begins, precisely because of how many step packages it could silently affect at once.
- Whether any actual Chapters 4-9 decision table uses section 2.11's second ("row × column intersection") style wasn't confirmed either way, beyond "not observed in the tables documented so far" - if `extract_tables.py` is ever pointed at a table that turns out to need this format, its current caption-position-and-wrapped-row-merge approach (built and tuned against condition/rule-style tables) would need real changes, not just tuning.
