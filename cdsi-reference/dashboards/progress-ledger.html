2026-09-09 - Phase 22 - Role B Round 19 - Unit 5.1 Closed: 3 of 4 Gaps Fixed, 4th Deferred With Measured Evidence (SPEC-4.6-0029) reviewed

Second unit tackled under the JUnit-first strategy, continuing forward from unit 4.4 (round 18). status.yaml's pre-existing notes for 5.1 (SelectRelevantPatientSeries) had already diagnosed all four gaps driving its 7 red tests precisely enough to act on directly. Fixed three cleanly: (1) Table 5-4 condition 0 ("does the indication describe any active patient observations?") was a hardcoded NO stub - now reads the patient's MedicalHistory for a matching ObservationCode. (2) Table 5-4 Rule 3 was encoded with its first condition as ANY instead of UNKNOWN, making the "flag for clinician" outcome a strictly weaker copy of Rule 2's ordinary "does not apply" outcome - fixed by encoding UNKNOWN, which the (now-implemented) condition never returns, correctly making Rule 3 unreachable via this path. (3) Table 5-5's own gender-check condition read caGender/caRequiredGender attributes that were only ever populated on its LT54 children, never on LT55 itself - both stayed null, so the condition always took its "no required genders" early Yes regardless of the series' actual restriction. Now LT55 gets its own copies, populated the same way. The fourth gap - AntigenSeries.getRequiredGenderList() never being populated by DataModelLoader from the series-level <requiredGender> element - was confirmed and a fix written, but measured (not assumed) to be unsafe to ship alone: Patient.getGender() carries ForecastInput's raw "F"/"M" vocabulary with zero normalization, while Supporting Data's <requiredGender> values are "Female"/"Male"/"Unknown". Adding the missing parsing branch alone caused a 388-case FITS regression - 100% in HPV, 0 improvements - because every gender-restricted series (all 4 of the bundled release's HPV series) flipped to "not relevant" for every patient, including the correct gender, once the comparison actually started running against never-matching strings. Reverted in full; a fresh FITS run confirmed the revert restores the exact 3-gaps-fixed baseline (3511 passed, 0 changed cases). This is deliberately NOT bundled into the same round: fixing it safely requires deciding where "F"/"M" <-> "Female"/"Male"/"Unknown" normalization belongs, a cross-cutting question that also touches 4.10 EvaluateGender's own separate (and separately flagged as likely dead) gender comparison over a third domain type. Recorded as SPEC-4.6-0029 (open) with the regression already measured, so whoever picks it up next has the exact blast radius in hand rather than needing to rediscover it. Final verification: unit 5.1's own suite 23/23 green (up from 16/23); full engine suite 127 failures/1 error (down from 134/1, sorted-diff- confirmed as exactly those 7 tests); full FITS run for what was actually shipped: 3511 passed both before and after, 0 changed cases - the fixture format carries no PatientObservation/MedicalHistory data at all, so fix (1) is FITS-inert for the same reason SPEC-4.6-0026's CALCDT-5 fix was, and fixes (2)/(3) are inert only because of the deferred fourth gap. Second consecutive round with zero regressions in what actually shipped, and the second round in a row where a mid-flight discovery (a second, unrelated defect one level deeper) was investigated, measured, and explicitly deferred with evidence rather than either blindly shipped or silently dropped.

2026-09-09 - Phase 22 - Role B Round 18 - Strategic Pivot to JUnit-First, and Unit 4.4 Closed Clean (SPEC-4.6-0028) reviewed

After three consecutive investigation rounds (HepA, ROTA, MCV) each surfaced a genuine, well-evidenced defect without any of them reaching a clean 100% FITS group, the project owner called a strategic pivot: stop hunting for FITS-group wins and instead work forward through the Logic Specification unit by unit, clearing every failing JUnit test starting at 4.4 (the first unit with reds). Cross-section changes are now explicitly permitted (no longer confined to one unit's own files) as long as each round stays bounded and understandable, and a FITS regression is now acceptable *if the team is confident the underlying fix is correct* - explicitly citing Chapter 8's SPEC-4.6-0020 rewrite as precedent, where the old behavior was accepted to be replaced despite a transitional regression because it was "all wrong." Unit 4.4 (EvaluateAndForecastAllPatientSeriesTest) was the first target. status.yaml's own pre-existing notes had already diagnosed two defects precisely enough to fix directly: (1) moveToNextTargetDoseIfAvailable() only checked "is this dose recurring?" once the target dose list was exhausted, using whichever dose was last rather than the one just satisfied, so nine mid-series recurring COVID-19 doses never got their duplicate; (2) markRestAsExtraneous() looped from aarPos + 1 rather than aarPos, silently dropping the first genuinely leftover antigen administered record instead of marking it EXTRANEOUS. Fixing both passed all 3 targeted JUnits cleanly (a sorted diff of the full 783-test suite showed exactly those 3 tests flip and nothing else), but the following full FITS run produced a severe regression: 3451 -> 3211 passed (-245 regressions against only 19 improvements), with HIB/VAR losing their forecasts entirely ("No forecasted vaccine group matched CVX n") and DTaP/HepB/MMR keeping a forecast but with wrong dates/status. Per this round's own new discipline - a regression this size needs its mechanism explained before being accepted or reverted, not just measured - the cause was root-caused by direct code reading rather than reverting on the strength of the number alone: the recurring-dose check fired unconditionally on every call to moveToNextTargetDoseIfAvailable(), including for SKIPPED doses (which never consumed an AAR). A SKIPPED dose with recurringDose=Yes whose duplicate is *also* SKIPPED on its own turn re-triggers the same check forever, tripping EvaluateAndForecastAllPatientSeries's own MAX_TOTAL_CYCLES/MAX_REPEATED_STATE_CYCLES loop guards and forcing an early, incomplete transition to SELECT_BEST_PATIENT_SERIES - exactly matching HIB/VAR's symptom. Gating the check to only fire for SATISFIED/SUBSTITUTED/UNNECESSARY outcomes fixed it. That in turn exposed a third, pre-existing defect that had been invisible until now: markRestAsExtraneous()'s placeholder TargetDose objects get their Evaluation set to EXTRANEOUS but never get their own TargetDoseStatus set, leaving it at the class default of NOT_SATISFIED. Table 7-10's completion check (DetermineForecastNeed) scans the whole target dose list for any NOT_SATISFIED entry, so every leftover-AAR placeholder wrongly forced its series to NOT_COMPLETE. This was invisible before because the off-by-one bug (fix #2) meant a series with exactly one leftover AAR created zero placeholders - fixing the off-by-one is what first exercised it. Fixed by explicitly setting each placeholder's TargetDoseStatus to UNNECESSARY - the closest existing value (Table 3-2 defines no target-dose-level "extraneous" status at all, confirmed via this project's own statuses.md concept doc) and otherwise dead code in the current implementation. Final verification: unit 4.4's own suite 21/21 green (0 red, down from 3); full engine suite 134 failures/1 error (down from 137/1, sorted-diff-confirmed as exactly the 3 targeted tests and nothing else); full FITS run case-by-case diffed against the true pre-fix baseline (not the intermediate, loop-guard-tripping attempt): 3451 -> 3511 passed, **0 regressions, 60 improvements** (51 DTaP, 9 COVID-19). The HIB/VAR/HepB/MMR cases that regressed under the first, incomplete attempt show zero net change against the true baseline once defect 1 was correctly gated - that regression was entirely self-inflicted by an incomplete first pass within this same round, not a pre-existing condition, and was fully resolved before merging. This is the cleanest round of the whole campaign so far by the new standard: zero regressions, meaningful net improvement, and a self-inflicted mid-round regression caught, explained, and corrected rather than either shipped blindly or reverted reflexively.

2026-09-09 - Phase 21 - Role B Round 16 - HepA Investigation: CALCDT-5 Date-Math Bug Fixed (SPEC-4.6-0026), Two Remaining Failures Are a Spec-vs-Fixture Conflict and a Supporting-Data Gap reviewed

Requested directly: get one FITS group to pass completely, starting with HepA (a simple schedule, only 4 failures at the time). Found and fixed a genuine, real date-arithmetic bug (SPEC-4.6-0026), plus a third CVX-equivalence gap in the same family as Round 13/14's - but HepA cannot reach 100% without either a project-owner ruling on a spec-vs- fixture conflict or new CDC Supporting Data content, neither of which is something engine code can resolve. All 4 of HepA's failures traced back to the exact same underlying computation - a dose administered 08/29/2026, HepA's minInt of "6 months," landing on a nonexistent 02/29/2027 (2027 is not a leap year) - split across two genuinely different problems: 1. SPEC-4.6-0026 (fixed): TimePeriod.getDateFrom()'s CALCDT-5 handling ("a computed date which is not a real date must be moved forward to first day of the next month") read the day-of-month back from the Calendar object *after* already setting its month/year fields with the original day still in place - but Calendar.set(MONTH, ...) doesn't clamp an out-of-range day, it silently rolls the excess forward (day 31 landing on a 28-day February becomes March 3rd, not February 28th or March 1st). The dedicated CALCDT-5 check could therefore never fire correctly; the answer produced was whatever Calendar's own overflow arithmetic happened to compute, which only coincidentally matches CALCDT-5 for a 1-day overflow (like this HepA case, and like the smaller of the specification's own two worked examples) and not for a larger one (the specification's other worked example, 08/31 + 6 months, was actually wrong by 2 days before this fix - 03/03/2001 instead of the specified 03/01/2001). Fixed by capturing the day-of- month before any month/year mutation and only then checking it against the target month's real maximum. Two new TestTimePeriod tests pin the specification's own worked examples plus the HepA-observed case; full cdsi-engine suite unchanged (identical failure set via sorted diff); full FITS run: 0 regressions, 0 improvements - the multi-day- overflow case this fix actually corrects does not occur anywhere in the current fixture set, only in the hand-authored test pinning the spec's own example. A real, worthwhile correctness fix regardless. 2. Not fixed - a genuine spec-vs-fixture conflict: three HepA fixtures (AART-EXTRA-3/5/7) all expect 02/28/2027 for this exact computation, directly contradicting CALCDT-5's own literal text and worked examples (both of which compute 03/01/2027, correctly, both before and after this round's fix). This cannot be resolved by further engine changes - the specification text is unambiguous, and these fixtures disagree with it. Needs a project-owner or CDC/CDSi decision about whether these "Extra Test Cases" fixtures are authoritative for this scenario, not something Role B can decide unilaterally. 3. Not fixed - a Supporting Data completeness gap: HepA's fourth failure (AART-EXTRA-10) throws IllegalArgumentException: Unrecognized cvx code '143' - confirmed absent from every antigen file and the schedule-level CVX map in the entire bundled 4.65 Supporting Data release, not just HepA's own file. This is correct, defensive engine behavior given the input; the gap is in the Supporting Data content itself (a future CDC/ACIP release, or a fixture ahead of what's bundled), not something engine code or a CvxEquivalence table entry can fix without fabricating vaccine registry data. Also fixed while investigating: CvxEquivalence's HepA group was missing CVX 82 (adult formulation) alongside its existing 85 (unspecified) and 52 (pediatric) - the same class of gap as Round 13/14's CVX 122/314 fixes. Added to both cdsi-fits-tests' CvxEquivalence.java and cdsi-web's FitsServlet.java. This alone did not flip AART-EXTRA-10's outcome, since that case fails earlier (the CVX-143 exception above), before the equivalence table is ever consulted. Net effect: HepA remains at 4 failures (96/100 passing, 96%), unchanged from before this round in raw pass count, but for well-understood, fully-documented reasons rather than an open question - one is a real, now-fixed engine bug with no FITS-visible effect yet, one needs a project-owner ruling, and one needs new Supporting Data. No FITS group reached 100% this round; the closest remaining candidates are worth a fresh survey once SPEC-4.6-0026's sibling question is resolved.

2026-09-09 - Phase 21 - Role B Round 13 - SingleAntigenVaccineGroup Aggregation (SPEC-4.6-0022) and a CVX-Equivalence Data Bug (RSV Was the Worst-Performing FITS Group) reviewed

Requested directly: with SPEC-4.6-0020/0021 shipped, RSV had become the single worst-performing FITS group (92% failure rate, 46/50 cases), worse even after those two rounds' PCV recovery. Investigated why. Two independent, previously-hidden defects were found and fixed, both exposed (not caused) by SPEC-4.6-0020's series-group loop the same way SPEC-4.6-0021 was: 1. SPEC-4.6-0022: SingleAntigenVaccineGroup (9.2) built one VaccineGroupForecast before its loop over the best patient series list and mutated that same shared object once per matching series, so whichever match was evaluated last silently overwrote every earlier match - both the status and, separately, the earliest date (which SINGLEANTVG-2 explicitly requires as a minimum across ALL matches, not a copy from one). Before SPEC-4.6-0020, an antigen never had more than one best patient series, so this was invisible. RSV's general "RSV 1-dose series" (no age bounds) and its "RSV 75 years+" alternate are not declared equivalentSeriesGroups to each other, so both routinely survive as separate best patient series for the same antigen - exactly the shape this bug needed. Fixed by collecting every match, choosing the most favorable status (Complete/Immune over an actionable Not Complete over a dead-end Contraindicated/Aged Out/Not Recommended - deliberately not MultipleAntigenVaccineGroup's own "any Aged Out wins" precedence, which answers a different question), and taking the true minimum earliest date across every match per SINGLEANTVG-2's literal text. SingleAntigenVaccineGroupTest already had both defects pinned as red tests from an earlier Role A pass (20/22 now green, was 16/22); the full engine suite incidentally dropped from 139 to 137 failures because those same two tests are counted there too. 2. A second, unrelated bug the same investigation surfaced while verifying fix 1 had zero FITS effect on its own: cdsi-fits-tests' CvxEquivalence.java (and cdsi-web's FitsServlet.java, the source it was copied from) declared CVX 122 - Rotavirus's own code, confirmed against the bundled Supporting Data - as equivalent to RSV's CVX 304.
