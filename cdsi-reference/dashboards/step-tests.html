MATERIALITY OF THE UNRESET SCORE - the key deliverable of this unit, now recorded in full in the 2026-09-02 cross-cutting entry. Answer: under the implementation as it stands, the accumulation CANNOT change which patient series 8.7 selects. Four facts, each verifiable by reading source rather than by a unit test (which always starts from 0 and so cannot settle it, as 8.6's update correctly said): (1) the score has exactly one reader in the engine and it is 8.7 - getScorePatientSeries() appears twice, both in this class, and addScore/setScorePatientSeriesScore are called by nothing - so no condition anywhere reads the score and a series' per-pass delta is independent of what it already carries; (2) every antigen pass presents 8.1-8.6 identical input, because 8.1 reads only the never-re-scoped all-antigen stepper and never reads dataModel.getAntigen(), 8.3 filters nowhere and so routes to the same one of 8.4/8.5/8.6 every time, 8.5/8.6 read that same stepper, and nothing in Chapter 8 mutates PatientSeriesStatus or anything else those steps read; (3) therefore score_i = M * d_i, with d_i the single-pass delta and M a single global pass count (global because 8.2 short-circuits a whole pass for everybody or nobody); (4) 8.7's comparison is invariant under that scaling - multiplying every candidate by the same positive M moves neither the maximum nor the tie set, so both SELECTBEST-2 clauses reach the same answer a single pass would. selectbestOneAnAccumulationScaledEquallyAcrossCandidatesDoesNotChangeTheWinner (green) pins step 4 on both a three-way ranking and a genuine tie; red 1 above pins the counterfactual.

The consequence is a sequencing constraint rather than a fix: this is non-material ONLY because the Chapter 8 scoping defect makes every pass identical, so the two open cross-cutting entries currently cancel each other. Re-scoping 8.5/8.6 per antigen or per series group is safe (each series would then be scored once).
