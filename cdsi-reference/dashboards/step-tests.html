4.2Organize Immunization Historytests written9 passed 2 failednot started-

Section 4.2 declares no business rules and no decision tables - it is "a fairly simple iterative process" of three numbered steps around Figure 4-3, with Tables 4-2/4-3 as a worked before/after example. The 11 tests cover all three numbered steps plus the two explanatory notes: a combination product expanded into one antigen administered record per antigen it contains (all sharing the dose's date and pointing back at it); a single-antigen product producing exactly one record; the record carrying the source dose's data elements (date administered, vaccine type, manufacturer, trade name, amount, lot expiration date, dose condition - note 2b); sorting by antigen; sorting by ascending date within an antigen; the whole Table 4-2 history organizing into all 19 Table 4-3 rows in Table 4-3's stated order; an empty history and an antigen-less product each producing no records; the unconditional transition to 4.3; and note 2a's age-based CVX-to-antigen association, from both sides.

9 green, 2 red. Both red tests are note 2a and fail for the same single reason - zosterLiveGivenBelowFiftyYearsIsAssociatedWithVaricellaOnly (expected [Varicella], actual [Varicella, Zoster]) and zosterLiveGivenAtOrAboveFiftyYearsIsAssociatedWithZosterOnly (expected [Zoster], actual [Varicella, Zoster]). Note 2a requires the CVX to Antigen Supporting Data's Association Begin Age / Association End Age to select the antigen by the patient's age at administration ("a Zoster vaccine administered below 50 years should be associated with Varicella"), and CVX 121 in the bundled releases does carry those attributes (Varicella [0 days, 50 years), Zoster [50 years, -)). OrganizeImmunizationHistory creates a record for every antigen in vda.getVaccine().getVaccineType().getAntigenList() with no age filter, so one CVX 121 dose always yields both records at any age. For Role B: the cause is not confined to this step's class - DataModelLoader.readCvx reads only the <antigen> child of each <association> and discards associationBeginAge/associationEndAge, and VaccineType holds a plain List<Antigen> with nowhere to put them, so the association ages never reach this step at all. Role A records this as observation only, with no finding filed and no classification attempted.

Deliberately not covered - (a) Figure 4-3's own activity-diagram data element list: both extracted copies of the figure image are blank, so the record's contents are tested against note 2b's prose and what the AntigenAdministeredRecord(vda, antigen) constructor documents rather than against the diagram; (b) the comparator's case sensitivity (it compares names with equalsIgnoreCase for equality but case-sensitive compareTo for ordering, and is technically inconsistent when an antigen is null) - the specification says nothing about either, and no real Supporting Data antigen name exercises them; (c) null immunization history / null administration date, which NPE - not behaviour 4.2 documents.

The two note-2a tests are the only ones that load a bundled CDC supporting data release (the way DataModelLoaderTest does); everything else uses hand-built domain objects. That load is unavoidable there, since the Association Begin/End Age attributes exist only in the release XML and in no hand-buildable domain object.

4.3Create Relevant Patient Seriestests written15 passednot started-

Section 4.3 defines no inputs, no business rules and no decision tables of its own, and says so explicitly: 4.3 and Chapter 5 share the title "Create Relevant Patient Series", and it is Chapter 5 (5.1, Tables 5-2/5-4/5-5, CALCDTIND-1/CALCDTIND-2) that holds the actual relevance logic. 4.3 itself is a paragraph in Chapter 4's processing-model overview that the specification deliberately leaves as orchestration - "similar to gathering necessary data (section 4.1), create relevant patient series will likely vary from system to system." So, as with 4.1, there is no normative rule here to mismatch, and the 15 tests pin the step package's documented State Changes and Next Steps instead - i.e. that CreateRelevantPatientSeries is the loop driver around 5.1, not a decision step.

Covered: the first call builds antigenSelectedList from every antigen on the data model and starts at position 0, delegating to 5.1 with the first antigen in place for 5.1 to read; every antigen is visited exactly once, in the data model's antigen-list order, one delegation to 5.1 per antigen; the loop then transitions to 4.4, and stays at 4.4 on further calls rather than wrapping or reading out of bounds; subsequent calls reuse the same selected-list instance and only advance the position counter; no antigens at all skips straight to 4.4 without ever delegating; the caller-supplied antigen label filter restricts the loop to the named antigens, while a null, empty, unmatched or differently-cased filter all fall back to every antigen; the selected list holds the Supporting Data Antigen instances themselves (5.1 compares antigenSeries.getTargetDisease() against them); antigens the patient has no dose for are still iterated; and driving the whole loop leaves every piece of Chapter 5 state untouched (antigenSeriesSelectedList, selectedPatientSeriesList, current antigen).

15 green, 0 red. No spec-vs-code gap found for this unit. Considered fully covered for what 4.3 itself documents.

Deliberately not covered - (a) the specification's State Changes sentence "each antigen series relevant for the patient is turned into a relevant patient series... those not relevant are excluded from further processing": that decision is made entirely in 5.1, which this step only delegates to, so testing it here would be a 5.1 test wearing a 4.3 label - only the negative is asserted (4.3 creates no patient series and selects no antigen series itself); (b) literal antigen iteration order: DataModel.getAntigenList() is built from a HashMap's values, so the order is not specified by anything and asserting a fixed one would be brittle - the tests assert instead that the loop visits exactly the data model's antigen list, each entry once, in whatever order that list reports; (c) running 4.3 against a real loaded Supporting Data release - the step reads nothing but the antigen map, so a hand-built model exercises every branch and a real release would only make it slower.

Three observations for Role B, none of them a code defect and none recorded as a finding. (1) The step package's State Changes says the first call builds the list from "all antigens the patient has data for"; the code actually iterates every antigen in the loaded Supporting Data, independent of the immunization history. The code is right - filtering to antigens the patient has data for would suppress forecasts for everything never administered - so this is a documentation imprecision in index.md, pinned by antigensThePatientHasNoDataForAreStillIterated. (2) transitions.yaml states the 5.1 branch's condition as "the antigen-selected list has not been built yet, or more antigens remain to iterate"; the first clause is not sufficient on its own - with zero antigens the first call builds the list and goes directly to 4.4, which is what noAntigensAtAllSkipsStraightToEvaluateAndForecast pins. (3) Every subsequent call also calls dataModel.incAntigenAdministeredRecordPos(), which State Changes does not mention ("just advances the position counter", singular). That field is written by this one line and read nowhere else in cdsi-engine or cdsi-web - the evaluation loop reads the distinct selectedAntigenAdministeredRecordPos - so it is currently inert vestigial code. Pinned as-is by subsequentCallsAlsoAdvanceTheUnrelatedAntigenAdministeredRecordPosition so the behaviour is recorded before anyone starts reading that field; not classified, per Role A scope.

Also pinned, each labelled in the test javadoc as having no specification counterpart: the SKIPPED/SUBSTITUTED/UNNECESSARY arms of the TargetDoseStatus switch, the SKIPPED-in-forecast transition from transitions.yaml, the "don't advance the record until Chapter 6 has recorded an evaluation" guard, and the two loop guards (>1000 cycles, >200 repeated states) the step package's Review Findings flags.

18 green, 3 red. (1) everyRecordLeftUnevaluatedWhenTargetDosesRunOutIsMarkedExtraneous - expected both records left un-evaluated to be EXTRANEOUS, actual only the last one: markRestAsExtraneous() loops from aarPos + 1, but aarPos already points at the first un-evaluated record because the SATISFIED arm incremented it before calling moveToNextTargetDoseIfAvailable(), so the first leftover record is skipped. (2) anExplicitlyNonRecurringLastTargetDoseAlsoMarksTheRestExtraneous - expected the two leftover records to be EXTRANEOUS, actual none at all: moveToNextTargetDoseIfAvailable() only calls markRestAsExtraneous() when the series dose has no RecurringDose object at all; an explicit recurringDose of "No" returns false without marking anything. Every seriesDose in the bundled Supporting Data releases carries a recurringDose element (62 of 62 in HepB) and DomUtils maps "No" to YesNo.NO, so in production the marking path is never reached and no record is ever set EXTRANEOUS by this step. (3) satisfyingARecurringMidSeriesTargetDoseAlsoCreatesAnotherOne - expected a satisfied recurring target dose to create another target dose (Figure 4-6 asks "is this target dose a recurring target dose?" of every satisfied dose, and only the No branch reaches "is there another target dose to process?"), actual no duplicate is created unless the target dose list is already exhausted, and the recurring flag consulted at that point is the last dose's rather than the recurring one's. Not hypothetical: the bundled releases contain nine non-final series doses with recurringDose Yes (all COVID-19). The assertion is deliberately position-agnostic - it asserts only that the duplicate exists - because Figure 4-6 does not say where "another target dose" goes, and this step package's State Changes ("inserted immediately after it") and the implementation (appended at the end) read that differently; the placement question is the ambiguous part and is left untested.

Deliberately not covered: (a) the ALERT.MISSING "currentPatientSeries is null" -> END transition, which is unreachable through the public API - process() increments the stepper whenever it is unstarted, so hasCurrent() true implies getCurrent() non-null, and forcing it would mean reaching into Stepper's private position rather than testing 4.4; (b) the ALERT.INVARIANT out-of-range aarIndex and empty-target-dose-list alerts, which are log-only and similarly unreachable without corrupting the data model by hand; (c) what Chapters 6 and 7 do once dispatched to - the tests assert only which step 4.4 hands off to and what state it leaves behind, and never call process() on the returned step; (d) a full multi-series drive of the loop to completion, which would need a stand-in for every Chapter 6/7 step and would be an engine test rather than a 4.4 test.
